# キーボード表示中は #root を visual viewport に追従させ、ページを scrollTo で戻さない

- Status: accepted
- Date: 2026-10-24
- Task: T314（ADR-20261023-1720 のキーボード対策の方式を差し替える）

## Context

iPhone PWA の実機で、オーナーから報告があった（2026-10-24）。入力欄を手動でタップすると、入力欄が画面の上へ外れていく。
スクロールし直すと戻るが、同じ状態から再び画面外へ出せてしまう。

従来の実装は、`visualViewport.resize` のたびに `#root` の高さを visual viewport の高さへ縮め、`window.scrollTo(0,0)` を呼んでいた。
iOS はキーボードが出ても layout viewport を縮めない。その代わりに、フォーカスした要素を見せるため visual viewport を下へパンする（`offsetTop > 0`）。
`#root` は通常フローで文書の先頭にあるので、パンした分だけ見えている範囲の上へずれる。`scrollTo(0,0)` はこのパンを戻せないうえ、
iOS 自身のフォーカス時スクロールと競合する。また html/body にスクロールの余地が残るため、手動スクロールで再び外へ出せる。
これらは観測された症状と矛盾しないが、実機では切り分けていない（推定）。

## 選択肢

1. `#root` を `position:fixed` にし、`top` を `visualViewport.offsetTop`、`height` を `visualViewport.height` に追従させる。
   html/body の overflow を止める。`scrollTo` はやめる。
2. 従来の方式を残し、`scrollTo` を `requestAnimationFrame` で遅らせて iOS のスクロールの後に呼ぶ。
3. `interactive-widget=resizes-content` に任せ、JS での追従をやめる。

## 評価基準

- iPhone PWA 実機で、入力欄をタップしたとき入力欄が見えている範囲に留まること。
- 手動スクロールで入力欄を画面外へ出せないこと。
- キーボードを閉じたら元の全画面に戻ること。
- デスクトップと fine pointer 環境には影響しないこと（自動テストで確認する）。

## 決定

選択肢 1。

## 理由（考察。比較実験は実機が要るため、実機での確認をもって検証とする）

- 2 は iOS のスクロールとの時間順序に依存し、パン自体は残る。端末や OS の版によって再発しうる。
- 3 は、iOS Safari が `interactive-widget` を実装しているかを一次資料で確認できていない。もともと 1720 で JS 追従を
  導入した理由（iOS PWA ではレイアウトが縮まない）が残っているため、採らない。
- 1 は、パン量（offsetTop）をそのまま `#root` の位置に反映するので、イベントの到着後には見えている範囲と一致する（定常状態での位置補正）。
  ただし iOS のフォーカス時のパンやキーボードのアニメーション自体は止めないため、遷移中の揺れや、WebKit が再びパンする可能性は実機で確認する。
  `#root` の中のスクロール容器（チャット履歴）はそのまま使える。
- 既知のリスク: ピンチズーム中（KI-2、KI-8）も offsetTop と height が変わる。現在はピンチ自体が効かないため影響しない。
  ピンチを有効化するときに、`vv.scale` で分ける必要がある。

## 検証

- 自動テスト: CSS 変数の追従、`scrollTo` を呼ばないこと、COARSE 外では何もしないことを確認した（18 件が通過）。
  変異 4 種（scroll リスナーの削除、offsetTop の無視、fixed の削除、旧実装の条件付き scrollTo の復活）でテストが赤になることも確認した。
- 実機: 2026-10-24、オーナーが iPhone PWA で確認し「問題なさそう」と回答した。
  確認を依頼した項目は次のとおり。項目ごとの結果や数値の記録は受け取っていない。
  - 初回のフォーカスと再フォーカス
  - キーボードを閉じた後に全画面へ戻るか
  - 履歴の上端・下端でのドラッグ
  - 縦横の回転
  - キーボード表示中のセーフエリア下余白
